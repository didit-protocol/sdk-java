# Contributing

This is the official Didit Java and Kotlin SDK. It follows [docs/DESIGN.md](docs/DESIGN.md), the contract shared by all seven Didit server SDKs: when the code and the design disagree, the code is wrong.

## Setup

- JDK 21 to build (the code compiles to Java 11 bytecode). Gradle downloads other JDKs for the test matrix when they are missing.
- Python 3.10 or newer for the code generator (standard library only).

## Commands

| Task | Command |
|---|---|
| Regenerate the generated layer | `python3 codegen/generate.py` |
| Check that it is up to date | `python3 codegen/generate.py --check` |
| Generator tests | `python3 -m unittest discover -s codegen/tests -t codegen` |
| All tests and checks | `./gradlew build` |
| Tests on another Java version | `./gradlew test -PtestJavaVersion=11` |
| Core coverage (90 % gate) | `./gradlew jacocoTestCoverageVerification` |
| Live sandbox smoke tests | `DIDIT_SANDBOX_API_KEY=... ./gradlew liveTest` |
| Format | `./gradlew spotlessApply` |
| Javadoc | `./gradlew javadoc` |
| Examples and Kotlin tests | `./gradlew :examples:build` |
| Quickstart against a local mock | `./gradlew :examples:quickstartDemo` |
| Spec sync, by hand | `python3 codegen/spec_sync.py --summary /tmp/summary.md` |

## Layout

- `openapi/`: the API contract. `verification.json`, `account.json` and `webhook-vectors.json` are upstream copies, never edited by hand; `overlay.json` holds the SDK naming (DESIGN 4); `deprecated-operations.json` (when present) keeps removed operations for one minor version.
- `codegen/`: the generator (Python). It reads only `openapi/`.
- `src/main/java/me/didit/resources`, `src/main/java/me/didit/types`, `src/test/java/me/didit/resources`: generated. Every file starts with `Code generated by codegen from openapi/*.json. DO NOT EDIT.`
- `src/main/java/me/didit/core`, `errors`, `webhooks`, `authentication` and `Didit.java`: the hand-written core.
- `examples/`: runnable examples and webhook receivers, built in CI.

## Changing the SDK

- Never edit generated files: change `codegen/` or `openapi/overlay.json` and regenerate. CI fails when the committed code is stale.
- A new API operation without a name fails the generator with a message naming it; add an entry to `openapi/overlay.json` (or ask for `x-didit-sdk` upstream).
- Public API changes need tests, README updates and a conventional commit type that matches their semver impact (`feat:`, `fix:`, `feat!:` or a `BREAKING CHANGE:` footer).
- A change to core behaviour that DESIGN.md describes (client options, errors, retries, pagination, webhooks, Authentication) is made in all seven SDK repositories, one pull request each, and DESIGN.md changes in all seven in the same words.
- Unit tests never touch the network. Use synthetic data only; webhook secrets in tests start with `whsec_test_`, and Authentication keys are generated at test time.

## Spec sync

`.github/workflows/spec-sync.yml` runs daily. When the published API documents change it regenerates the SDK, runs every check and opens a pull request titled `chore(spec): sync API spec YYYY-MM-DD`, with the added, removed and changed operations and schemas. Removed operations stay, deprecated, until the next minor version; the contract test fails once that version is reached, as a reminder to delete them.

You can push commits to the sync branch (for example hand-written webhook or Authentication changes): while the open sync pull request has a commit of yours, the workflow leaves it alone. Keep the `BREAKING CHANGE:` footer of the sync commit when you merge. The workflow reads the branch with its token, so it also works while the repository is private; if that read fails, the run fails instead of rebuilding the branch.

## Releases

Releases are cut by release-please from conventional commits; `CHANGELOG.md` is generated and never edited by hand. Nothing is published before Alex approves the first release, and not before 2026-11-01; until then versions stay `0.x`.

1. The workflow `.github/workflows/release-please.yml` is off until the repository variable `RELEASES_ENABLED` is `true`.
2. On each push to `main`, release-please updates a release pull request (version in `gradle.properties`, `Version.java` and the README, plus `CHANGELOG.md`).
3. Merging it creates the `vX.Y.Z` tag and the GitHub release. The `publish` job then waits for a reviewer of the `maven-central` environment, runs `./gradlew check`, signs and uploads to Maven Central (Central Portal), and attests the jars.
4. If a publish fails after the tag exists: when the cause is outside the code (an expired token, a missing secret, a Central Portal outage), fix it and rerun the failed `publish` job of that workflow run. A rerun builds the tag's commit, so it never picks up a fix merged to `main` later; when the code has to change, merge the fix to `main` and release the next patch version instead.

One-time setup by a repository admin, before the first release:

- Maven Central: the `me.didit` namespace verified on central.sonatype.com, and a Central Portal user token.
- A GPG signing key, with its public key on a key server.
- Repository secrets `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`, `MAVEN_SIGNING_KEY` (ASCII-armored private key) and `MAVEN_SIGNING_KEY_PASSWORD`.
- A `maven-central` environment with required reviewers and "Prevent self-review".
- Optionally `RELEASE_PLEASE_TOKEN` and `SPEC_SYNC_TOKEN` (a GitHub App or fine-grained token), so CI runs on the release and sync pull requests.
- Finally, the variable `RELEASES_ENABLED=true`.
