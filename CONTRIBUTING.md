# Contributing

This is the official Didit Java and Kotlin SDK. It follows [docs/DESIGN.md](docs/DESIGN.md), the contract shared by all seven Didit server SDKs: when the code and the design disagree, the code is wrong.

## Setup

- JDK 21 to build (the code compiles to Java 11 bytecode). Gradle downloads other JDKs for the test matrix when they are missing.
- Python 3.10 or newer for the code generator (standard library only).

## Commands

| Task | Command |
|---|---|
| Regenerate the generated layer | `python3 codegen/generate.py` |
| Check that it is up to date | `python3 codegen/generate.py --check` |
| Generator tests | `python3 -m unittest discover -s codegen/tests -t codegen` |
| All tests and checks | `./gradlew build` |
| Tests on another Java version | `./gradlew test -PtestJavaVersion=11` |
| Core coverage (90 % gate) | `./gradlew jacocoTestCoverageVerification` |
| Live sandbox smoke tests | `DIDIT_SANDBOX_API_KEY=... ./gradlew liveTest` |
| Format | `./gradlew spotlessApply` |
| Javadoc | `./gradlew javadoc` |
| Examples and Kotlin tests | `./gradlew :examples:build` |
| Quickstart against a local mock | `./gradlew :examples:quickstartDemo` |
| Spec sync, by hand | `python3 codegen/spec_sync.py --summary /tmp/summary.md` |

## Layout

- `openapi/`: the API contract. `verification.json`, `account.json`, `authentication.json`, `webhook-vectors.json` and `breaking-vectors.json` (sdk-python's, copied byte for byte) are upstream copies, never edited by hand; `overlay.json` holds the SDK naming (DESIGN 4); `deprecated-operations.json` (when present) keeps removed operations for one minor version. Nothing is generated from `authentication.json`: the `authentication` package is hand-written (DESIGN 10) and `AuthenticationContractTest` holds it to the document.
- `codegen/`: the generator (Python). It reads only `openapi/`. `codegen/tests/pinned/` holds earlier upstream copies of `verification.json`, pinned by commit, for the spec sync tests.
- `src/main/java/me/didit/resources`, `src/main/java/me/didit/types`, `src/test/java/me/didit/resources`: generated. Every file starts with `Code generated by codegen from openapi/*.json. DO NOT EDIT.`
- `src/main/java/me/didit/core`, `errors`, `webhooks`, `authentication` and `Didit.java`: the hand-written core.
- `examples/`: runnable examples and webhook receivers, built in CI.

## Changing the SDK

- Never edit generated files: change `codegen/` or `openapi/overlay.json` and regenerate. CI fails when the committed code is stale.
- A new API operation without a name fails the generator with a message naming it; add an entry to `openapi/overlay.json` (or ask for `x-didit-sdk` upstream).
- Public API changes need tests, README updates and a conventional commit type that matches their semver impact (`feat:`, `fix:`). `feat!:` or a `BREAKING CHANGE:` footer is only for a change to the SDK's own design (DESIGN 13), never for a change that mirrors the API.
- A change to core behaviour that DESIGN.md describes (client options, errors, retries, pagination, webhooks, Authentication) is made in all seven SDK repositories, one pull request each, and DESIGN.md changes in all seven in the same words.
- Unit tests never touch the network. Use synthetic data only; webhook secrets in tests start with `whsec_test_`, and Authentication keys are generated at test time.

## Spec sync

`.github/workflows/spec-sync.yml` runs daily. When the published API documents change it regenerates the SDK, runs every check and opens a pull request titled `<type>(spec): sync API spec YYYY-MM-DD` (DESIGN 3.1 and 13):

- `feat(spec)` when a caller can observe the change (an operation, parameter, field, enum value or response shape): a minor version, even when the change can break typed code. Never `!` or a `BREAKING CHANGE:` footer.
- `chore(spec)` when only descriptions, examples or other documentation changed: it releases nothing on its own.

The body opens with "Breaking changes", the changes that can break typed code that `codegen/spec_sync.py` detects (or "None detected"), then lists the added, removed, renamed and changed operations and schemas. It ends with a `BEGIN_COMMIT_OVERRIDE` block that release-please reads instead of the merged commit: the sync line plus one `api(spec):` line per breaking change, which `release-please-config.json` puts under "API changes that can break typed code". Merge it with **Squash and merge** and keep the block; after a merge commit, every line would appear twice in the release notes. When hundreds of breaking changes do not fit the description, it has no block and says so: squash with the message of the sync commit, which holds every line.

The breaking changes follow the rules of DESIGN.md 3.1, so that all seven SDKs list the same ones: `codegen/tests/test_breaking_vectors.py` runs the sync on every case of `openapi/breaking-vectors.json`. A media type a request body or response no longer has is compared with the one that replaces it, so a field only it carried (a multipart file) counts as removed. A union variant's Java name can come from its title or description (`model.Builder._union`), so a documentation change that renames one is `feat(spec)` too; the body lists it under "Java union variant names", not under "Breaking changes".

Removed operations stay, deprecated, until the next minor version; the contract test fails once that version is reached, as a reminder to delete them. When `authentication.json` adds, removes or renames an operation, the summary says so and `AuthenticationContractTest` fails until the hand-written module follows.

You can push commits to the sync branch (for example hand-written webhook or Authentication changes): while the open sync pull request has a commit of yours, the workflow leaves it alone. The workflow reads the branch with its token, so it also works while the repository is private; if that read fails, the run fails instead of rebuilding the branch. A manual run (`workflow_dispatch`) syncs the branch it was started from; for a branch other than `main` it uses its own sync branch, `chore/spec-sync-<branch>`, and opens its pull request into that branch, so close that pull request once you have looked at it.

## Releases

Releases are cut by release-please from conventional commits; `CHANGELOG.md` is generated and never edited by hand. The first release, 1.0.0, shipped on 2026-10-29 with Alex's approval; every release after that publishes straight from the repository (DESIGN 13).

1. The workflow `.github/workflows/release-please.yml` runs while the repository variable `RELEASES_ENABLED` is `true` (set since 1.0.0). Merging the release pull request is the release approval (Alex, 2026-10-29); nobody tags or publishes by hand.
2. On each push to `main`, release-please updates a release pull request (version in `gradle.properties`, `Version.java` and the README, plus `CHANGELOG.md`).
3. Merging it creates the `vX.Y.Z` tag and the GitHub release. The `publish` job then runs in the `maven-central` environment (it holds the secrets; no reviewers), runs `./gradlew check`, signs and uploads to Maven Central (Central Portal), and attests the jars.
4. If a publish fails after the tag exists: when the cause is outside the code (an expired token, a missing secret, a Central Portal outage), fix it and rerun the failed `publish` job of that workflow run. A rerun builds the tag's commit, so it never picks up a fix merged to `main` later; when the code has to change, merge the fix to `main` and release the next patch version instead.

One-time setup (done for 1.0.0 on 2026-10-29):

- Maven Central: the `me.didit` namespace verified on central.sonatype.com, and a Central Portal user token.
- A GPG signing key, with its public key on a key server.
- Secrets of the `maven-central` environment: `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`, `MAVEN_SIGNING_KEY` (ASCII-armored private key) and `MAVEN_SIGNING_KEY_PASSWORD`.
- A `maven-central` environment holding those secrets, with no required reviewers. The Central Portal token expires on 2027-04-29: generate a new one and replace the two secrets before then.
- Optionally `RELEASE_PLEASE_TOKEN` and `SPEC_SYNC_TOKEN` (a GitHub App or fine-grained token), so CI runs on the release and sync pull requests.
- Finally, the variable `RELEASES_ENABLED=true`.
